# 프론트엔드 스트레스 테스트

## 테스트한 데이터 조건

- 추천 업무 0개, 1개, 8개, 9개
- 200자 이상의 요약과 60자 이상의 영업 단계
- 100자 이상의 업무명과 여러 문단의 업무 설명
- 고객 요구사항 11개, 근거 발언 5개, 필요 자료 11개
- 빈 요구·우려·약속·확인 배열
- 기한·권장 시점·근거·필요 자료·신뢰도 누락
- 신뢰도 `-0.4`, `1.7`, `null`
- 정의되지 않은 실행 방식 `workshop_orchestration`
- Mock 분석 실패
- 기존에 없던 업무명과 파일명

## 발견한 화면 문제

1. 음성 파일은 정보만 표시되고 Mock 결과 선택에는 사용되지 않았다.
2. 추천 업무가 없으면 분석 전 대기 화면과 구분되지 않았다.
3. 빈 분석 배열도 제목만 있는 섹션으로 표시됐다.
4. 신뢰도 누락·범위 초과 값이 직접 계산되어 오류 또는 잘못된 백분율을 만들 수 있었다.
5. 다수 업무의 카드 영역 높이가 제한되지 않았다.
6. 사용자 직접 업무 추가와 거절 상태가 없었다.
7. 저장 데이터에 승인 업무만 남아 수정·거절·사용자 추가 결과를 평가할 수 없었다.

## 수정한 내용

- 파일 별칭 및 안정적인 fingerprint를 이용한 Mock 시나리오 매핑
- 8개 대조군과 실패·장문·누락 데이터 추가
- 분석 결과 정규화 및 신뢰도 clamp
- 알 수 없는 실행 방식을 `맞춤 업무`로 안전하게 표시
- 빈 배열 섹션 생략, 0개 업무 전용 안내
- 다수 업무 영역 스크롤과 긴 텍스트 줄바꿈
- 사용자 업무 추가, AI/사용자 출처, 사용자 수정 여부 표시
- 승인·보류·거절 상태와 평가 데이터 유지
- 버전 3 LocalStorage workspace 저장과 녹취 출처·수정 여부 보존
- 새 분석 초기화 확인과 개발용 진단 영역

## 아직 남은 프론트엔드 위험

- Mock 파일 매핑은 음성 내용을 인식하지 않는다. 실제 음성 내용에 따른 결과는 STT/AI 연결 이후에만 검증할 수 있다.
- 브라우저 기본 확인 대화상자의 표현은 브라우저마다 다를 수 있다.
- 매우 큰 실제 분석 JSON은 현재보다 더 높은 메모리와 렌더링 비용을 만들 수 있다.
- 실제 AI가 필수 객체 자체를 완전히 다른 타입으로 반환하는 경우 계약 경계에서 추가 스키마 검증이 필요하다.

## 실제 AI 연결 전 확인 사항

- 다양한 실제 응답을 정규화 계층에 통과시킨 계약 테스트
- 필수 식별자 중복 여부와 최대 payload 크기
- 긴 문자열·배열에 대한 제품 한도와 축약 정책
- 잘못된 개별 업무를 제외할지 `확인 필요`로 유지할지에 대한 운영 원칙
- 개인정보가 진단 JSON과 LocalStorage에 남지 않도록 하는 정책
